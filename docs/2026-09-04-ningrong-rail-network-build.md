- 计划文档：`docs/superpowers/plans/2026-09-04-ningrong-real-route-display-mode.md`
- 分支/提交：`codex/real-rail-routes-pilot`，`c4dd2b9`（试点）+ `8740690`（六安修正）
- 产出：`tools/build_rail_route_data.py`（构建脚本）、`js/rail-route-data.js`（15 节点 / 14 区段 / 553.4km 网络）、`js/rail-routes.js`（寻径纯函数）、地图曲线/真实路径双模式

本文记录从零构建「车站/线路所为节点、相邻节点间为物理区段」铁路网络的全过程：方法、踩坑与解法，供扩展其他走廊时复用。

## 一、总体管线

```
Overpass 抓取(geom 模式, 分窗口)
  → 节点定义(客运站 + 线路所, 坐标以正线几何核验)
  → 区段定义(way 名称过滤 + via_ways 渡线 + unnamed 补缺)
  → way 图构建(端点容差合并 → 加权超边)
  → Dijkstra 寻径(分量感知) → 折线
  → DP 显示简化 + 完整折线里程
  → 校验(端点对齐/连通性/里程区间/车次走线)
  → 原子写 JS
```

### 1.1 数据抓取

- **用 `geom` 模式导出**：way 元素自带 `geometry` 坐标数组，免去按 node ref 二次取点，处理代码大幅简化。
- **按地理窗口分片抓取**（南京—合肥—汉口走廊拆 6 片，每片 170–540 ways），单片过大会超时或被限流。
- **镜像与重试**：overpass.private.coffee 实测较稳，统一 6 次重试。
- **抓取缓存**：`op_*.json` 入 `.gitignore`、本地保留——构建脚本可离线重跑，原始数据不进仓库（ODbL 署名随 `rail-route-data.js` 分发）。

### 1.2 网络建模

- **节点两类**：客运站（`source=data`，与 data.js 站表坐标一致，保证站点标记对齐）与线路所/岔点（`source=osm`，直接用 OSM 坐标）。
- **区段定义三要素**：
  - `ways`：参与匹配的 OSM way 名称集合（同一条物理线在不同图源可能叫「沪蓉线」「合武绕行线」等）；
  - `via_ways`：站场咽喉区的短渡线按名称精确直取，避免寻径在岔区游荡；
  - `unnamed_files`：允许 unnamed way 参与特定区段（站区/联络线常见无名 way）。

### 1.3 寻径——本项目最大的方法论修正

**v1（贪心链式，失败）**：种子吸附最近 way → 逐步取端点最近的相邻 way 延伸。两种死法：
1. 南京南 data.js 坐标 1.9km 内有东侧截断段，容差从 0.008° 放宽到 0.02° + 多起点重试仍选中它；
2. 合肥南编组站岔路密集，链子游荡 346 步回到起点（护栏强退时已积累 908 个点）。

**v2（way 图 Dijkstra，成功）**：放弃「逐步延伸」思路，把每条 way 整体作为一条加权超边（权重 = haversine 长度），way 端点按容差合并为图节点后求最短路。贪心的每一步局部最优陷阱，在全局最短路下自动消失。平局（等长路径）取字典序小的区段序列，保证结果确定性。

**双线铁路的关键特性**：上下行是两条**不共享端点**的平行链，直接建图会分成多个连通分量（本项目实测 4 个：273/152/32/3）。解法：BFS 标注分量 → 起终点候选仅在同分量内配对（配对池 `pairs[:20]` 逐对重试）。

### 1.4 简化与里程分离

- 显示用 Douglas-Peucker 简化（容差 0.0009° ≈ 90m，显式栈实现）；
- **里程一律用简化前的完整折线**按 haversine 累计——简化是为渲染性能，不能让渲染精度污染里程数据。

### 1.5 校验体系（分两层）

| 层 | 校验 | 拦住的问题 |
| --- | --- | --- |
| 几何 | 折线端点与节点坐标对齐 <0.001° | 拼接断口 |
| 几何 | 连通性（全部节点互达，15/15） | 分量断裂、缺口 |
| 几何 | EXPECTED_KM 区间表（14 区段逐条） | 寻径选错绕行线 |
| 业务 | 走廊区段计数表（8/9/1/10/10/7/3） | 区段聚合错位 |
| 业务 | 真实车次走线断言（G1427 不进汉口支线、G1747 首段走合武绕行、G1184 不含雷麻店段） | 寻径语义错误 |

**已知盲区**：「端点对齐通过」≠「几何正确」——六安尖刺（见 2.4）就是端点严丝合缝地对到了一个偏离正线 3.5km 的坐标上。建议补一条**端点偏移告警**：折线端点到相邻点距离 >2km 即在生成期报错。

## 三、核心经验（给下一条走廊的自己）

1. **先想数据形态，再选算法。** 铁路 OSM 数据的四个特性——双线平行不共端点、岔区端点微差、站区正线缺口、命名不稳定——决定了链式拼接必然失败，图寻径是唯一稳妥解。容差（合并 5e-4°、种子 0.02°）要按数据实测分布定，不要拍脑袋。

2. **坐标来源优先级：正线 way 几何 > OSM station 节点 > data.js 站表。** 三种来源都出现过公里级偏差（六安 3.5km、雷麻店 1.8km、data.js 通病 ~1-3km）。任何坐标入网前，用「距正线最近顶点」核验，偏 >2km 必须修正。

3. **校验要分层，业务校验不可省。** 几何校验（对齐/连通/里程）全绿不代表走线正确——G1427 该走京广联络线不该进汉口支线这类语义错误只有车次级断言能拦住。反之，车次断言依赖的计数表来自真实时刻表，是业务 ground truth。

4. **缺口处理套路**：先 min/max 对比定位缺口 → 补抓窗口 → 缺口内无名 way 放行 → 仍断则怀疑「并行段被标成别的线路名」（坑 7 最隐蔽）→ 站区小缺口用连线中点桥接 + 注释坐标留复核线索。

5. **工程护栏**：EXPECTED_KM 区间表让寻径回归有硬标准；生成产物原子写（写临时文件再替换）避免半截文件；抓取缓存与生成产物分离（缓存不进库，产物进库带署名与快照日期）。

## 四、复现与扩展指南

重新生成（需 managed Python venv 含 openpyxl）：

```
python tools/excel_to_js.py          # Excel → js/data.js（记录/站表）
python tools/build_rail_route_data.py # op_*.json → js/rail-route-data.js
node --test tests/*.test.js          # Node 全量回归
python -m unittest discover -s tests # Python 全量回归
```

扩展新走廊步骤：
1. Overpass 按窗口抓取新走廊（geom 模式，存 `op_<name>.json`，gitignore）；
2. 定义节点（客运站查 data.js 站表并**贴线核验**，岔点取 OSM）；
3. 定义区段（way 名称集合 + 渡线 + unnamed 补缺），跑构建看连通性；
4. 断口按「缺口处理套路」逐个消（新走廊几乎必有 1-3 个）；
5. 定 EXPECTED_KM 区间 + 车次走线断言，补进 `tests/rail-routes.test.js`；
6. 全量回归后提交，**收尾再核验一次分支引用**。
