# 高铁实际路径绘图：代码审查与实现建议

审查日期：2026-09-05。主要基线为 `main...3786135`；审查期间新增的 `2772aa8`（六安坐标与站区折线修复）已单独核对。以下构建、寻径、缓存问题仍存在于 `2772aa8`。本次仅生成报告，没有修改业务代码或生成铁路数据。

结论：保留 ECharts 和离线线路数据分发是合理的。当前问题主要出在铁路拓扑的构造、线路归属约束、站点坐标与记录级路径管理；继续放宽吸附距离、补直线、修剪折返，不能稳定解决这些问题。建议先修确定性错误，再把原始轨道图、展示区段图和行程路径分开。

## 已确认的问题

### 1. P1：构建单条线路时实际在整个网络上寻径，线路归属会被污染

位置：`tools/rail_network/build.py:520–547`，尤其是传入 `stitch_line` 的全局 `waygraph`；相关提取逻辑在 `tools/rail_network/extract.py:101–119`。

`osm_names` 只决定哪些 way 加入整个网络，没有约束某条线路的相邻站应走哪些 way。随后无论实际经过哪条线，`cut_line_segments` 都直接赋予正在构建的 `lineIds`。

使用本地缓存 `rail-extract-8d514a7230e3e939.json` 和基线构建函数复现：

- 京沪线路的南京南→镇江南，返回路径使用了 1 条沪蓉线 way、15 条仙宁线 way、79 条沪宁城际线 way、17 条京沪高铁 way。
- 苏州北→昆山南也混入沪宁城际线。

这些计数是实际执行时追踪 `_chain_pts` 得到的，不是根据地图外观猜测。全网图当然需要允许跨线，但构建“指定线路区段”必须约束主线归属，并显式允许必要的枢纽联络线；不能把任意全网最短路重新标成该线路。

### 2. P1：Dijkstra 找到的边与最终绘制的边可能不是同一条

位置：`tools/rail_network/geometry.py:325–348`、`292–313`；兜底 `_dijkstra_all` 也只保存前驱节点。

算法只记录节点序列，丢掉了所选 way 的索引。拼接折线时重新查找两个节点间的第一条边。上下行线、渡线等存在平行边时，第一条边未必是 Dijkstra 松弛时选中的边。

最小复现：同一对端点间先放入 3.145 km 的折线，再放入 2.224 km 的直线。Dijkstra 距离是 2.224 km，但 `route()` 返回 3.145 km 的折线。实际南京南→镇江南追踪中，50 处所取平行边的权重大于同端点的最小边权。

应在前驱中保存 `(prevNode, wayId/edgeId, direction)`，直接用这条边重建路径，常规与兜底寻径都要修改。

### 3. P1：虚拟补桥的权重单位错误，且用坐标接近代替真实连通

位置：`tools/rail_network/geometry.py:179–185`、`86–117`；调用参数见 `tools/rail_network/build.py:526`。

普通边权使用公里，但 `bridge_zone()` 将经纬度欧氏距离 `d` 直接放入邻接表。最小复现中，一条实际长 1.112 km 的桥，权重只有 0.01，被当作 10 米。构建器还把补桥半径放大到 `0.015°`，本地缓存上实际新增了 600 条虚拟桥；“线路总长不过分绕行”的校验无法识别这种更短的错误捷径。

此外，原始提取丢弃了 OSM node ID，仅合并 way 首尾约 55 米内的坐标：真正共享内部节点的分岔可能断开，物理不相通的邻近轨道则可能连上。最小复现中，两个不同端点只因相距 `0.0001°` 就被合为同一分量。

立即修复边权为 `haversine_km`；随后以 OSM node ID 建立真实连通，虚拟连接改为有来源、有明确端点的补丁清单。修正单位本身不能使所有虚拟桥变成真实铁路。

### 4. P1：线路所按距离和插入，已经生成错误站序与重复走廊

位置：`tools/rail_network/build.py:234–247`。

`insert_via_stops` 比较的是“前站到线路所 + 线路所到后站”，没有减去原站间距离，也没有使用沿线顺序。它偏好原本间距较短的站对。

用基线宁蓉站表直接调用，局部结果是：

```text
肥东 → 长安集 → 雷麻店 → 合肥南 → 六安
```

保留的原有区段顺序则是：

```text
肥东 → 合肥南 → 长安集 → 雷麻店 → 六安
```

产物因此同时包含 `leimadian-hefei-south`（27.91 km）、`hefei-south-nan-fen-lu`（50.76 km）等新增长段与原有分段。即使默认最短路暂时避开某些边，网络仍存在重叠表示，影响新增中间站行程、热度聚合与候选路径。

近期可直接声明线路所位于哪个站对之间；长期依据已经验证的线路链里程插入，不再用空间距离猜站序。

### 5. P2：同起终站不等于同一物理区段，目前会丢失多路径

位置：`tools/rail_network/build.py:442–449`；`validate` 在 `681–683` 也禁止同端点多边。

合并键只有无序站名对。两条不同线路连接同一对车站时，第二条折线被丢弃，只把线路标签和较早开通日期并入第一条。

直接调用 `cut_line_segments`，先输入甲→乙的北侧折线，再输入甲→乙的南侧折线，最终只剩北侧折线，但其 `lineIds` 同时包含南、北两条线路。

应允许站对之间存在多个稳定区段 ID。只有来源轨道链、端点切分位置和物理走廊均一致时才合并。否则，后续选径界面无法找回已经在生成期被删除的备选路线。

### 6. P2：真实模式的站点标记与线路仍读取两套坐标

位置：`js/app.js:843–857`、`1890–1905`；`js/rail-routes.js:56–66`。

折线使用网络节点，静态标记和回放站点使用 `stations[name]`。已有 `stationCoord` 没有接入这些调用点，而且其优先级仍是旧站表在前。

固定基线测量有 19 个站相差超过 100 米，例如北京南 973 米、天河机场 818 米、郑州东 617 米、红安西 544 米。部署启动还会用 `/api/train-data` 的站表覆盖随仓库发布的数据，因此仅修改 `js/data.js` 不保证已有部署对齐。

真实模式应统一使用经过线路验证的锚点，静态站点、悬停、动画起终点共同消费；曲线模式可继续使用原业务坐标。新增网络内车站的坐标识别也应接入同一入口。

补充：审查期间曾观察到六安标记与端点相差约 2.55 km，这是其他工作先修改站表、后修改产物的暂时状态，不是固定基线的点线不一致。`2772aa8` 已同步六安两套坐标并修改站区折线；本报告不把该瞬时差异计为待修缺陷。

### 7. P2：记录级路径缓存以起终站为键，会覆盖不同车次的选径

位置：`js/app.js:765–778`、`790–794`，键定义在 `634–635`。

缓存键是 `from→to|trainType`，没有日期、车次或路径选择。纯寻径函数支持的 `date/train` 覆盖，在地图集成后可能失效：先处理的记录会决定后面同站对记录的线路。

使用真实函数和四节点测试网络，G1 应走 `ab,bd`，G2 有覆盖应走 `ac,cd`；单独调用均正确，经 `cachedRecordRoute` 依次调用后，G2 得到 `ab,bd`。这会污染热度、悬停和回放。现有 G1435 覆盖与当前自动结果相同，不能用它证明缓存正确。

应按稳定记录 ID 与选径、网络版本缓存。记录解析完成后，再按物理区段聚合；不要先按站对去重再解析。

### 8. P2：区段开通日期没有参与寻径

位置：`js/rail-routes.js:87–94`、`239–244`。

`serviceDate` 已写入产物，但构造邻接表和寻径均未过滤记录日期。输入 2020-01-01 的池州→黄山西记录，会返回库中 2024-04-26 开通的池黄区段，78.2 km，并计为真实路径覆盖。

自动候选和人工选择都需要验证行程日期；不满足条件时应返回不确定或曲线兜底。开通数据本身也需复核：当前 `date_overrides` 有跨多站范围，而 `stitch_line` 只按相邻站对精确查找，范围覆盖不会自动展开。

### 9. P2：人工覆盖只检查 ID 存在，没有检查是一条完整路径

位置：`js/rail-routes.js:126–131`、`199–226`。

甲→丁的人工覆盖只给甲→乙一个区段，仍返回成功，路径停在乙；两个不连续的合法 ID 也可能被按坐标远近拼成跨越缺口的直线。现有覆盖优先级测试甚至用未到汉口的短区段作为南京南→汉口的“成功”预期。

应从出发节点按有向区段逐步检查连续性，验证最终抵达目的节点、日期可用和每个连接的坐标一致性。不合法的覆盖要明确返回失败或回退，不能仅靠点到端点距离猜方向。

## 为什么现有检查拦不住

- 固定 `3786135` 快照的 Node 测试 174/174、Python 测试 29/29 全部通过。
- 新增 `2772aa8` 后复核铁路测试 31/31 通过。`tools/diag_equiv.py` 的严格逐点等价检查为 13/14，通过不了的是六安→金寨：旧数据 24 点、生成数据 15 点，生成结果恰好等于旧数据再次 Douglas–Peucker 简化并取 5 位小数的结果；完整折线长度差约 0.06 米。这是严格等价约定与重新简化的冲突，不据此认定线路走错。
- Python 测试没有覆盖新增的铁路几何与构建模块。许多前端集成测试只断言函数名或源码片段存在，不能验证缓存和实际渲染数据。
- `validate()` 构建了邻接表但没有遍历连通分量。两个完全断开的区段仍输出“校验通过”。应验证每条必要线路/站对可达；全国网络存在合法独立分量时，不应机械要求所有节点强行连成一张图。
- 端点检查仅比较折线首尾与节点，不能证明中途沿轨行驶。先把折线端点改为节点坐标，当然容易通过此检查。
- `cut_line_segments:428–430` 的 `dist(...) < 2.0` 单位是度，注释却写小于 2 km；可允许约两百公里量级的端点改写。应使用显式公里/米函数，且对改写前的偏移单独校验。
- `osmium` 和 `pypinyin` 被构建器导入，却没有列入构建依赖。当前默认 Python 中二者也未安装；`requirements.txt` 只有 `openpyxl`。本次使用已有提取缓存复现构图和局部寻径，没有执行完整 PBF 重新提取及全网写出。构建依赖宜独立固定版本，PBF 路径可配置，缓存指纹绑定实际输入校验值与提取版本。

光点范围：`buildLineSeries` 的常驻移动光点已经关闭；回放中的 `trip-head` 和到站阶段 `tripLineSeries` 的光点仍保留。后者是当前实际行为，不据此推断必须删除。

## 推荐实现：保留离线展示，重做数据构建与选径层

```mermaid
flowchart LR
    A[固定 OSM 快照] --> B[按 node ID 构建轨道图]
    B --> C[验证线路归属与车站接入]
    C --> D[切分稳定物理区段]
    D --> E[按日期和途经站生成候选]
    E --> F[每条行程保存选择]
    F --> G[ECharts 展示与热度聚合]
```

### 轨道图：保留来源与连接关系

继续使用 pyosmium，但提取 `wayId`、有序 `nodeRefs`、坐标及相关标签，在共享节点和车站切入处拆边。先保留上下行和平行线路，验证连通后才压缩无分岔的连续边；不把轨道的空间接近当作道岔。pyosmium 已提供包含节点 ID 和坐标的 `NodeRefs`，现有提取代码可以保留这些信息。[pyosmium 官方数据模型](https://docs.osmcode.org/pyosmium/latest/user_manual/02-Extracting-Object-Data/)

保留线路归属、`service`、`usage`、`highspeed`、桥隧等可用标签，以区分主线、侧线、站场和真实渡线。不能只筛选 `highspeed=yes`，否则可能漏掉动车实际使用的联络或共线区段。标签的字段语义参考 [OSM 铁路规范](https://wiki.openstreetmap.org/wiki/Tag:railway%3Drail)；中国具体线路数据的完整性仍需逐线核验。

### 车站：选择正确线路，再投影到线段

保存业务车站位置与轨道锚点的区别。先依据站名、稳定 ID、线路归属和站区范围确定候选轨道，再做最近线段投影；仅找最近顶点会随 OSM 顶点密度漂移。Shapely 的 `line_locate_point` 支持先投影再给出沿线位置，可配合插值、切线使用。计算偏移阈值时用适当局部米制投影或测地距离，不把经纬度当米。[Shapely 官方文档](https://shapely.readthedocs.io/en/stable/reference/shapely.line_locate_point.html)

线路图使用同一锚点贯穿切分、标记与回放。保留原始轨道图，在展示层将经过核验的上下行归为同一物理走廊；不要在路由前把所有站场轨道合成一个可任意跨线的节点。

### 行程：候选线路与实际选择分开

仅有起站、终站和日期时，最短路是推测结果，不能证明某趟列车确实这样运行。优先级建议为：有效的用户选择 → 有来源的车次/日期/途经站匹配 → 自动候选 → 曲线兜底。

先按日期和线路约束生成少量无环候选，再按“经过哪些干线”去重。上下行轨道或同站场几米差异不能占满候选列表。1.25 倍长度可作为默认候选筛选阈值，不能作为真实路线的硬定义；用户已确认或停站序列能证明的较长路线仍应允许。

Python 可用 NetworkX 辅助实现候选算法。其 `shortest_simple_paths` 基于 Yen，但明确不支持 `MultiGraph/MultiDiGraph`；若直接保留平行边，需用带独立边节点的等价图或支持边 ID 的实现，不能为了调用函数先丢掉多路径。[NetworkX 官方文档](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.simple_paths.shortest_simple_paths.html)

可预留接口：

```js
findRouteCandidates(record, { limit: 3 })
// [{ id, edgeRefs, lineIds, points, km, resolution, warnings }]

record.routeChoice = {
  networkVersion: "...",
  edgeRefs: [{ id: "...", direction: 1 }],
  source: "manual"
};
```

选径界面展示“经哪些线路/主要途经站 + 估算公里 + 地图预览”。不要持久化“候选第 2 条”，因为重新构建后顺序会变；保存稳定边序列及网络版本，升级时重新验证，失效则提示重新选择。

当前 `normalizeRecord`、服务端保存字段和 Excel 往返都没有这类字段。实现选择器时需把它们一起打通，或使用按稳定记录 ID 关联的独立选径存储，否则刷新或导出再导入会丢失选择。几何缓存、记录路径缓存与热度聚合缓存应分别管理。

## 实施顺序与验收

1. **先修确定性错误。** 前驱保存边 ID；所有权重统一公里；限制或取消未核验虚拟桥；修正线路所顺序；构建线路时约束轨道归属；真实模式统一坐标入口；缓存改为记录级；验证人工覆盖与日期。
2. **再迁移构建器。** 从小范围重新保留 node refs，先验证南京/合肥/武汉等已暴露问题的枢纽；输出每段的来源 way、补丁和吸附偏移报告，再扩展全网。
3. **最后接入选径界面。** 保留多条物理走廊，生成按干线去重的候选，打通持久化与版本迁移。

优先补以下行为测试：平行边返回正确几何；桥权重等于测地长度；宁蓉线路所站序正确；京沪指定区段不混入未允许的线路；同站对双线路均保留；同站对不同车次的覆盖互不影响；图上站点与路线锚点一致；历史记录不能使用晚开通区段；不连续/不完整覆盖被拒绝。再用实际问题区段进行固定视口的地图检查，避免只验证总里程和覆盖条数。

小规模手工维护已核验的“相邻枢纽/站点区段 GeoJSON”也能先稳定现有行程，但全国扩展和中间站新增会增加维护成本。对本项目已计划的全国网络与行程选径功能，采用上述轨道拓扑与行程路径分层方案更合适；更换绘图库本身无法修复错误的坐标或连接关系。
